# deep-test 有效性分析

> **结论先行：** 不用本skill的普通测试做完后，deep-test 再用其 60% 的时间做一轮深度测试。评测中它找到的新问题全部成立，以中高危为主，而且能稳定补上再进行一次普通测试容易漏掉的几类问题：Web 接口以外的安全问题、数字格式变体、去重与归一化、时间边界。

评测对象：两个真实项目，项目 A 是 Python 命令行批处理工具，约 1.5 万行；项目 B 是 Python 后端加 TypeScript 前端的全栈 Web 应用，约 3.3 万行。共做了 6 次深度测试，每个项目还有 3 次独立的普通测试作为对照。

## 1. 正向作用

| 指标 | 结果 |
|---|---|
| 问题质量 | 每分钟找到的高中危新问题，是"再跑一次普通测试"的 1.3–1.8 倍 |
| 补盲区 | 3 次普通测试都没找到、只有 deep-test 找到的根因：项目 A 6 个，项目 B 10 个 |
| 方向命中 | 普通测试检出率最低的三类问题，正是 deep-test 必查清单覆盖的方向（见第 2 节） |
| 可控 | 6 次都没超出时间预算；不改项目代码；本机环境没有受到影响 |

## 2. 设计思路

此前尝试过两个方向，都不对：

- **best-test**：先整理需求基线，再按需求生成用例严格执行，由覆盖率门禁决定是否准出。评测中有没有这个 skill，结果都一样，耗时却约为 3.6 倍；门禁本身也能被绕过。
- **honest-test**：用一套完整的流程和检查清单约束代理"诚实、全面"地测试。按遗漏补规则，规则越写越长，单次召回却不上升；两次独立运行只重合约一半。

两者的共同问题是试图改写模型的整个测试过程。模型本身的测试能力已经很强，再加一套流程，很可能只是噪声。

评测数据也说明了这一点。下表按问题方向统计普通测试的检出率，即每类问题平均被 3 次普通测试找到的比例。普通测试在一部分方向上已经做得很好，短板只集中在少数几个方向：

| 检出率高（普通测试已够用） | 检出率低（deep-test 重点补） |
|---|---|
| 管理接口参数校验 87%、Web 接口认证授权 78%、代码检查工具输出 76% | Web 接口以外的安全 25%、数字和格式变体 27%、文本匹配和去重 30%、时间窗口 37%、持久化与状态 38% |

deep-test 反过来做：
- 普通测试一个字不改，让模型按自己的方式完整跑一遍；
- 之后单独加一轮查漏补缺：普通报告里已有的问题作为排除清单，只在模型经常遗漏的方向上用力，如 Web 接口以外的安全、数字格式变体、去重与归一化、时间边界、持久化、数据新鲜度。

这样不会削弱模型原有的测试能力，增加的只是它原本做不到的那部分。

## 3. 局限

- **数量上不占优。** 按全部新问题算，每分钟找到的和再跑一次普通测试相当。
- **证据有限。** 只测了 2 个项目。
- **成本。** 需要额外再测试一次。

## 4. 使用建议

- 项目要上线，需要注意安全性，或者处理金额、数量、外部输入等出错代价高的数据时，用 deep-test。
