# 深度测试清单

目标：在 B 的时间内，只找普通测试没找到的问题。安全检查每个档位都必做。

## 0. 规则

- 不改工程里的代码、测试和配置，不修 bug。自己写进工程的只有 `DEEP_TEST_REPORT_<yyyy-mm-dd>.md`；跑测试和脚本时工程自己生成的文件（缓存、输出等）不删，记进报告第 5 节。脚本、日志等临时文件放系统临时目录下的 `deep_test_<yyyymmdd-HHmm>/`，结束后保留不删。
- 报告里的每个数字都来自本次运行过的命令。
- 普通测试报告里已有的问题是排除清单，不重复报；同一根因换个说法、换个输入也算重复。每条入账前，在普通测试报告里搜它的文件名、函数名和关键词。
- 不写锁定测试；不并行派多个代理。

## 1. 开工

1. 记下开始时间 D0。B = 所选比例 × T。算出两个时刻：停止探测 = D0 + 0.75B，交报告 = D0 + B。
2. 读普通测试报告和子代理回复；之后按需读代码，用搜索定位，不通读。
3. 列缺口清单（第 3 节），连同 D0、B 和两个时刻写进临时目录的 `gaps.md`。
4. 每做完一项（缺口清单、每个安全项、每类缺陷、每次复现）查一次时间、重读 `gaps.md`。每得到一条新问题（含疑似）或线索，就追加到临时目录的 `findings.md`（新问题按报告第 2 节格式，线索按第 4 节格式）；每做完一项，在 `gaps.md` 里标为已做。停止探测的时刻之前不写报告：档位内容做完了，就继续做 `gaps.md` 里还没做的项，或按下一档的内容探测。到了停止探测的时刻，不再开新的探测，用 `findings.md` 写报告；没做的项写进报告第 4 节。

## 2. 档位

自填比例按不超过它的最大档位执行；低于 30% 时做 30% 档的内容，先做安全检查，仍按 B 停止。

| 档位 | 内容（逐级累加） |
|---|---|
| 30% | ① 缺口清单；② 安全检查（第 5 节，优先）：先在后台启动依赖审计，同时把其余各项各搜一轮，有可疑点再探测，30% 档不为探测专门启动服务；③ 对普通测试排名最高的模块，逐类搜索常见缺陷（第 4 节） |
| 60% | 再加：常见缺陷类型覆盖全部主要模块 |
| 100% | 再加：普通测试没打开过的模块；只读实时抓取（只调抓取部分，不进入发送和写入），包括逐个探测缺口清单里的更新通道是否可达、返回是否为空或过时（付费接口不探测）；复核普通测试的高危问题（结论写进报告第 4 节，不计入新问题） |
| 200% | 再加：实际制造并发和中断（多个进程同时写、写到一半终止）来验证第 4 节的持久化问题；配置组合等更深的探测 |

"排名最高的模块"：普通测试报告里高危问题最多的模块；报告没给出严重度时，取直接产生对外结果（计算、发送、写入）的模块。

## 3. 缺口清单（先做，要快）

对照普通测试报告列出：

- 没提到的模块和入口：列出源码文件和入口（主程序、命令行脚本、定时任务、Web 路由；不含虚拟环境、`node_modules` 和生成的目录），逐个在普通测试报告里搜文件名和模块名，搜不到的算没提到；
- 文档里能检查、但普通测试没核对的要求（包括 README，以及 AGENTS.md 等写给 AI 代理的说明文件里的规则，各工具的文件名不同）；
- 没覆盖的常见缺陷类型（第 4 节）；
- 没覆盖的安全检查项（第 5 节）；
- 需要持续更新的数据及其更新通道（从文档、计划任务和配置里找），写明每类数据应有的更新周期；工程没有这类数据就写"不适用"。

## 4. 常见缺陷类型

逐类用搜索命令找出全部相关位置再判断，不靠通读。这张表只是最低要求，不限于这些类型。

| 类型 | 找什么 |
|---|---|
| 失败被记成成功 | 批量循环、any/all 汇总、返回码映射、宽泛的异常捕获；错误页或拦截页被当成正常返回 |
| 数字和格式变体 | 正负号（减号、括号、"down/loss"）、千分位（空格、点、逗号）、单位与倍数、币种、语言区域、全角字符 |
| 过滤、去重、截断 | 误杀、误合并（不同的东西被判为相同，例如相似度判断忽略了数字、型号、地名）；归一化漏项（同义写法没归到一类，"A 和 B"这类列表只识别出一个） |
| 时间窗口和调度 | 回看窗口与调度周期不匹配；迟到运行、补跑、重试路径没走同样的检查；未来时间被当成最近；时区不同的时间直接比较或按字符串排序 |
| 持久化与状态 | 文件写到一半（末行不完整、进程中断）后再读写会不会出错或丢数据；读-改-写不是原子操作；异常路径不释放锁；更新时用空值覆盖已有字段；删除时不检查引用 |
| 数据新鲜度与更新通道 | 缺口清单里列出的每类数据：最新一条的时间与应有周期是否相符，时间序列有没有断档；各更新通道（订阅源、接口、计划任务）最近的运行记录是否失败、长期为空或停止运行；凭据、地址等配置是否已过期；项目能不能察觉这些情况（旧数据是否仍当最新展示，断流是否有提示或告警） |
| 配置 | 拼错的键、越界值不报错 |
| 测试本身 | 碰真实资源，或往仓库里写文件 |
| 文档与代码不一致 | 包括 AGENTS.md 等写给 AI 代理的说明文件里的规则 |

数据新鲜度只读数据文件和运行记录，不为此触发更新。数据本身过期，可能只是工程拷贝时的状态或环境没在运行，写进报告第 4 节作为数据观察；项目自己察觉不到过期或断流的（仍当最新数据展示、失败记成成功、没有任何提示），才计为问题。

## 5. 安全检查（每档必做）

每项都要有搜索或探测，结果写进报告第 3 节。工程没有某类功能（例如没有登录）时，写明搜索了什么、结果为空，记为"不适用"。

| 项 | 至少查 |
|---|---|
| 注入 | 外部数据拼进 shell 命令、SQL、HTML/模板、文件路径；`eval`/`exec`；不安全的反序列化（`pickle`、`yaml.load` 等） |
| 密钥 | 出现在代码、配置、日志、命令行或错误信息里；`.env` 等文件被提交 |
| 认证与授权 | 匿名访问、伪造或过期的令牌、已删除或降级用户的旧令牌、默认口令、登录不限速、CORS 带凭证 |
| 外发请求 | SSRF、关闭了 TLS 校验、请求不可信的 URL |
| 不可信输入源 | 邮件、订阅源、上传文件被当作可信数据（例如不核对发件人） |
| 依赖漏洞 | 用项目对应的审计工具（`pip-audit`、`npm audit` 等）审计项目实际运行的版本：有锁文件（`uv.lock`、`poetry.lock`、`package-lock.json` 等）就审计锁文件导出的清单；没有锁文件，就审计项目运行所用解释器（以文档或计划任务里写的为准）`pip freeze` 导出到临时目录的清单。不审计按声明范围重新解析出的版本，也不审计运行工具的临时环境。工具没有、又不能按第 7 节临时运行时记"未测" |

## 6. 验证与计数

- 用批量脚本：一个脚本测很多种情况，只输出不符合预期的结果。
- 每个不符合的结果，先看实际输出再计数。期望值注明来源：哪份文档的哪一行，或写明隐含要求。
- 只计有可观察的错误行为、可利用的风险，或会让人照着做错的文档不一致；错别字、格式、风格、"建议加强"不计。
- 一次修改就能一起修好的算一条，条目里写用例数和全部位置；要分别修改的各算一条。依赖漏洞一次审计算一条，条目里列出项目实际依赖中有漏洞的全部包、当前版本和修复版本；只用于开发和测试的包单独注明。
- 每条标"已复现"或"疑似（只读了代码）"。已复现＝本次命令的实际输出直接证明问题存在（运行结果、审计输出、搜到的明文密钥等）。严重度：高＝错误的对外结果（计算、发送、写入）、数据丢失、可利用的安全漏洞；中＝功能出错但范围小；低＝其余。高危必须复现；来不及复现的不降级，作为线索移到报告第 4 节。疑似不超过新问题的 30%，超出的要么复现，要么作为线索移到报告第 4 节。

## 7. 权限（只约束深度测试轮）

| 允许 | 有条件允许 | 一律不做 |
|---|---|---|
| 在工程里跑测试和脚本（先搜它会不会发邮件、写真实数据或调付费接口，会的按右边两格处理，确认不了就不跑；普通测试已跑过的整套测试不整套重跑，需要时只跑相关的测试文件或用例）；只读访问公开网站；依赖漏洞审计；读邮箱（只读：不标已读、不移动、不删除；报告里只引用定位问题所需的最少内容） | 发邮件：只有某条发现必须真实发送才能复现时才发，只发给项目文档或配置里明确指定的测试地址，发送前核对实际收件人列表只含这些地址，否则不发。项目文档明确列出的标准测试命令可以跑，即使会消耗大模型额度；其中发邮件或写数据的部分仍按本表其他各格处理。缺少的工具用 `uvx`、`pipx run`、`npx` 一次性运行，或装进临时目录里新建的虚拟环境 | 发给其他任何人；写生产环境或真实数据；使用其他付费服务；往项目或系统的解释器、全局环境里安装、升级、卸载包（含 `npm audit fix`）；在工程里生成锁文件 |
